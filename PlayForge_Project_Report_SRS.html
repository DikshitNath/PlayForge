1. Introduction

This document is the Software Requirements Specification (SRS) for PlayForge Studio, a web application and interactive prototyping laboratory designed for the theme: "Toys & Games - Challenges your creative minds to conceptualize and develop unique toys & games." It contains the technical specifications required to design, implement, test, and evaluate the system, organized according to the IEEE Std 830-1998 standard.

1.1 Purpose

The purpose of this SRS is to establish the complete functional and non-functional requirements of PlayForge Studio. The intended audience includes the software development team, academic course evaluators, STEM instructors, and maker community reviewers. It acts as the definitive contract for implementation, verification, and acceptance.

1.2 Scope

The software product is named PlayForge Studio. It is a responsive, server-rendered Django web application that structures the conceptualization, digital prototyping, and fabrication workflow of innovative toys and games.

PlayForge Studio will:

  • Provide an open invention directory allowing makers to draft and publish technical Invention Blueprints with explicit novelty factors, Bill of Materials (BOM), tools required, rules of play, and STEM curriculum mappings.
  • Execute real-time in-browser interactive prototypes within the PlayLab Virtual Arcade:
    • CogCraft: 2D physics sandbox with gravity ramps, bouncers, and acoustic pentatonic chimes synthesized via Web Audio API.
    • ChromaTiles: Tactical optical ray-tracing board game playable Hotseat 2-Player or vs an intelligent AI Bot.
    • GearSmith: Kinematic gear reduction and four-bar linkage simulator driving biomimetic puppet automata.
  • Provide the Spark Ideation Engine, a 4-dial combinatorial randomizer synthesizing target demographics, mechanical principles, unconventional materials, and narrative themes.
  • Organize Maker Design Challenges with strict engineering constraints (e.g., zero gravity play, single-sheet origami folding mechanisms).
  • Enable community playtesters to record multi-axis validation metrics (Fun, Originality, Durability, and STEM Value) with DIY maker modifications.
  • Generate print-ready, high-contrast Maker Specification Sheets (/print/) formatted for laser cutting and 3D printing workshops.

Objectives and Goals: Overcome creator's block through constraint-based ideation; validate physical toy kinematics in software before material purchasing; and provide teachers and makers with open-source educational blueprints.

2. General Description

2.1 Product Perspective

PlayForge Studio is an independent, self-contained Django web application. It bridges the gap between toy ideation, computer-aided simulation, and hands-on physical maker fabrication. It is organized into modular apps (creations, playforge) communicating through Django's Model-View-Template architecture, backed by SQLite in development and PostgreSQL in production.

2.2 Product Functions

At a summary level, the system performs the following core operations:

  • Blueprint Specification Management: CRUD operations on toy/game concepts with novelty factors, materials lists, and instructions.
  • Interactive PlayLab Simulators: Real-time physics engine, optical ray tracing, and gear kinematics running in client-side HTML5 canvas.
  • Combinatorial Ideation Machine: 4-dial randomizer with instant URL parameter transfer to the blueprint builder.
  • Design Challenge Arena: Publishing hackathon briefs with constraints and tracking competing entries.
  • Playtesting Telemetry: Recording multi-axis user review scores and maker hack suggestions.
  • Live Spark Upvoting: Asynchronous session-tracked voting without page reloads.
  • Monochrome Patent-Style Export: Print-optimized stylesheet for fabrication manuals and cut lists.

2.3 User Characteristics

User ClassCharacteristics & Needs
Toy / Game Inventor Maker, engineering student, or hobbyist seeking structured specification templates to define materials, novelty principles, and rules.
Playtester / Gamer Casual user or tabletop enthusiast testing mechanics in browser simulators and submitting gameplay ratings.
STEM Educator Teacher searching for physics or kinematics demonstrations with curricular mapping and printable maker sheets.
Administrator Faculty or platform staff managing design challenge briefs, moderating blueprints, and reviewing telemetry.

2.4 General Constraints

  • Implemented in Python 3 using the Django 6 framework with server-rendered templates.
  • Database utilizes SQLite for zero-configuration development and PostgreSQL for production deployments.
  • Interactive simulators are implemented using standard HTML5 Canvas 2D API without heavy external third-party physics engines.
  • Interface responsive from 360px mobile viewports to desktop resolutions.

2.5 Assumptions and Dependencies

  • Users have access to an evergreen web browser supporting JavaScript ES6, Canvas 2D, and Web Audio API.
  • Speakers or headphones are enabled for acoustic chime synthesis in the physics simulator.
  • Python 3.14 and pip package manager are installed on the host machine.

3. Specific Requirements

3.1 External Interface Requirements

3.1.1 User Interfaces

  • Engineered using Django templates, HTML5, CSS3, and Tailwind CSS with a clean, executive dark-mode palette.
  • Navigation bar provides access to Blueprints, PlayLab Arcade, Spark Engine, Challenges, and Concept Builder.
  • Interactive simulators feature dark hardware-grade canvas frames with real-time HUD metrics.

3.1.2 Hardware Interfaces

No proprietary hardware interface required. The software interacts with standard mouse, trackpad, and touchscreen pointers for drawing ramps and rotating prism tiles.

3.1.3 Software Interfaces

Software ComponentPurpose & Specification
Python 3 / Django 6Application framework, ORM, templating, session state
SQLite / PostgreSQLRelational persistence for blueprints, challenges, and reviews

3.1.4 Communications Interfaces

Standard HTTP/1.1 or HTTP/2 protocol. Form submissions use POST with mandatory CSRF protection tokens. Upvote counts communicate asynchronously via JSON over HTTP.

3.2 Functional Requirements

3.2.1 Invention Blueprint Management

SPEC-1: The system shall record and persist complete toy/game specifications including title, category, target age range, player counts, play duration, difficulty, materials, rules, and safety advisories.
SPEC-2: The system shall auto-generate unique URL-friendly slugs using slugify().
SPEC-3: Multi-line materials text shall be dynamically split into an iterable checklist array.

3.2.2 The Novelty Factor Analysis Engine

NOV-1: Every creation must supply an explicit novelty_factor field explaining what mechanical, physical, or strategic principle sets it apart from existing toys.
NOV-2: The novelty factor shall be displayed prominently in dedicated high-contrast callout boxes on detail and summary views.

3.2.3 PlayLab Arcade - CogCraft Physics Sandbox

SIM-1: The system shall simulate 2D gravitational kinematics ($\vec{v} += \vec{g}\Delta t$) and circle-to-line segment collision responses ($\vec{v}' = \vec{v} - 2(\vec{v}\cdot\hat{n})\hat{n}$).
SIM-2: When a steel ball collides with a sound chime, the system shall synthesize an acoustic sine wave tone at the designated pentatonic frequency using the Web Audio API.
SIM-3: The system shall allow users to place pegs, acceleration boosters, warp portals, and toggle continuous dispensers.

3.2.4 PlayLab Arcade - ChromaTiles Optical Strategy

OPT-1: The system shall ray-trace laser beams across an 8x8 illuminated grid from emitter origins $(0,0)$ and $(7,7)$.
OPT-2: Angled mirror tiles (45° Right ╱ or 45° Left ╲) shall reflect beam vectors at 90° angles.
OPT-3: Intersecting target sensor crystals shall score Energy Sparks for the beam owner.
OPT-4: The system shall support 2-player pass-and-play and single-player vs AI Bot ("Optic-1").

3.2.5 PlayLab Arcade - GearSmith Kinematics Lab

KIN-1: The system shall compute real-time gear tooth meshing with variable reduction ratios (e.g., 24T driving 48T for 2:1 reduction).
KIN-2: The system shall simulate eccentric cam linkages translating rotary speed into non-linear harmonic oscillations.
KIN-3: The system shall drive articulated biomimetic puppet models (Ornithopter bird wings and undulating Manta Ray fins).

3.2.6 Spark Ideation Engine

SPRK-1: The system shall combine four discrete random pools (Demographic, Mechanism, Material, Theme).
SPRK-2: The system shall synthesize composite titles, pitches, and novelty factors.
SPRK-3: Clicking "Send to Forge" shall pre-fill the creation form with generated spark parameters via URL query encoding.

3.2.7 Maker Design Challenges

CHAL-1: The system shall list active design challenges with specific engineering constraints (e.g., Zero-G Play, One-Sheet Origami).
CHAL-2: Creators may submit existing blueprints as competitor entries into active challenges.

3.2.8 Playtesting Review Matrix

REV-1: Playtesters shall record ratings (1-5 scale) across Overall, Fun Factor, Originality, Durability, and STEM Value.
REV-2: The system shall compute average review ratings dynamically.
REV-3: Reviewers may record DIY maker modification suggestions.

3.3 Non-Functional Requirements

  • Performance: Page responses shall render in under 150 ms locally. Physics and optics simulators shall maintain 60 FPS frame rate.
  • Reliability: 100% of automated unit tests shall pass without errors.
  • Security: Form submissions enforce CSRF protection. Input data is validated and sanitized against XSS attacks.
  • Maintainability: Modular Django app structure separating models, views, forms, and canvas prototypes.
  • Portability: Runs seamlessly across Windows, Linux, and macOS platforms.

3.4 Design Constraints

  • Server-rendered Django 6 MVT architecture in Python 3.
  • Pure HTML5 Canvas 2D implementation without external physics libraries.
  • Zero build-step front-end utilizing Tailwind CSS.
